Week 5 · Load Balancing

Half the Fleet Is Lying

  • Role: primary on-call
  • 3 decisions
  • ~15 min
Tue 14:10 SEV2 checkout-api 5xx rate 18.2% (threshold 1%)
Tue 14:10 fleet: 12/12 targets healthy (lb health check: GET /health → 200)
Tue 14:11 deploy log: checkout-api v412 rolled to 1/12 hosts (canary: ip-10-0-3-17)

Your first solo on-call shift. The checkout API runs on 12 servers behind a Layer 7 load balancer configured for least connections. A canary deploy went out 20 minutes ago to one host. The load balancer says all 12 hosts are healthy.

Something doesn't add up. If one host in twelve is bad, you'd expect about 8% errors, not 18%.

M

Morgan · Staff SRE · 14 years on-call

When the numbers don't add up, that's your best clue. Don't touch anything yet. First explain the 18%.

Decision 1 · 14:12

Why is one bad host causing 18% errors instead of 8%?

The failover drops every in-flight connection: about 2,300 checkouts reset at once. Error rate on the new load balancer? Still 18%. You've added a second incident on top of the first. Don't touch shared infrastructure until you can explain the symptom.

That's it. This is the black hole effect: a broken server that errors instantly looks like the least-busy server in the fleet. Least-connections and least-response-time algorithms reward fast failure. Its access log confirms it: the canary is serving 2.4x its fair share.

You pull the canary out of rotation. Errors drop to 0.1%.

Partly true: retries do amplify errors. But you spend 25 minutes looking at client retry configs while users keep failing. The bigger cause was the algorithm itself routing toward the broken host. Start from what's different about the bad host, then follow the traffic.

Whatever path you took, the canary is out and v412 is rolled back. The postmortem asks: why did the load balancer report a host serving 100% errors as healthy? Because /health only checks that the process is running. The canary's process was fine. Its database connection pool was misconfigured.

Decision 2 · Postmortem action item

How do you redesign the health check?

Three weeks later the payment provider has a 40-second blip. All 12 hosts fail their health checks at the same time, and the load balancer pulls the entire fleet. Browsing and search, which don't touch payments, go down too.

A deep health check turns a shared dependency's hiccup into a total outage. Health checks should answer "is this host broken?", not "is the world OK?"

Readiness catches a host that can't serve. Outlier detection catches the canary pattern: a host whose 5xx rate is 50x its peers'. The max ejection cap is the key detail. If everyone is failing, the problem is shared, and ejecting hosts can only make it worse. That's how Envoy and service meshes do it.

Now a dead host keeps getting traffic for up to 60 seconds × the failure threshold of 3, which is three minutes of black-holing. Health checks are cheap. Slow detection is not.

Two weeks later, product has a request: "Carts keep vanishing when users bounce between servers. Can we just pin users to one server?" A teammate opens a PR to turn on IP-hash sticky routing.

Decision 3 · Code review

How do you review this PR?

Brightcart's biggest B2B customer has 4,000 employees behind one corporate NAT IP. Every one of them hashes to the same server, which runs at 100% while the others idle. Meanwhile mobile users switch between Wi-Fi and cellular, their IP changes, and they land on a new server with an empty cart anyway.

Better. The cookie follows the user across IP changes. But when a host dies or autoscaling removes one, everyone pinned to it loses their cart. Stickiness also skews load, because long-lived heavy users pile up on old hosts. It treats the symptom.

You fixed the cause. With the state external, any server can serve any request, the balancing algorithm can do its job, and scale-in or a crash loses nothing. Stickiness is still occasionally useful as a performance optimization (warm local caches), but never as a correctness requirement.

What you just learned

Layer 4 vs. Layer 7

L4 (transport)L7 (application)
SeesIPs, ports, TCP/UDPHTTP: paths, headers, cookies
Can doVery fast forwarding, any protocolPath routing (/api vs /img), TLS termination, retries, cookie stickiness, per-request balancing
ExamplesAWS NLB, IPVS, MaglevAWS ALB, NGINX, Envoy, HAProxy (HTTP mode)
Use whenRaw throughput, non-HTTP, long-lived connectionsMost web traffic, microservice routing

Balancing algorithms and how each one fails

AlgorithmHow it worksFailure mode
Round robinEach server in turnIgnores load. A slow server still gets its full share
Weighted round robinTurns weighted by capacityWeights go stale as hardware changes
Least connectionsFewest open connections winsBlack hole: a fast-failing host attracts traffic
IP hashhash(client IP) → serverNAT hotspots, and mobile IPs change
Power of two choicesPick 2 at random, send to the less loadedFew. Near-optimal and cheap (used by Envoy and NGINX)
Consistent hashingHash ring. Adding or removing a node moves only ~1/N of keysNeeds virtual nodes to balance. Used for caches and shards

Health checks: liveness, readiness and outlier detection

  • Liveness: is the process alive? Failing means restart it.
  • Readiness: can this host serve right now (warmed up, pool connected, disk not full)? Failing means stop sending it traffic.
  • Outlier detection (passive): watch real traffic and eject hosts that error far more than their peers. Always cap the ejection percentage.
  • Fail open: if every target is unhealthy, many load balancers route to all of them anyway. When everything looks broken, the health check is probably what's wrong.

It happened for real

Real postmortems

Meta (Facebook, Instagram, WhatsApp)Oct 4, 2021 · ~6 hours

A command meant to assess backbone capacity accidentally disconnected Facebook's entire backbone. Then a health-check-style safety mechanism finished the job: Facebook's DNS servers are designed to withdraw their BGP route advertisements when they can't reach the data centers. They did exactly that, and every Facebook domain vanished from the internet even though the DNS servers themselves were running.

Lesson: "remove myself when I look unhealthy" is safe for one node. When every node runs the same logic against a shared dependency, they all remove themselves together. Same trap as Decision 2.

Source: Meta Engineering: More details about the October 4 outage

AWS Elastic Load Balancing · us-east-1Dec 24, 2012

On Christmas Eve, a maintenance process was accidentally run against production and deleted part of the ELB state data: the configuration that tells each load balancer which backends to route to. Affected load balancers were misconfigured for hours. Netflix streaming was among the high-profile casualties.

Lesson: the load balancer is also a system with state, a control plane and failure modes. Its config is production data and needs access controls and backups.

Source: AWS: Summary of the December 24, 2012 ELB Service Event

Field notes

Morgan's rules of thumb

  1. When the error rate is out of proportion to the number of bad hosts, suspect the algorithm.
  2. Health checks answer "is this host broken?" Never fail one because of a shared dependency.
  3. Cap automated ejection. If everything looks broken, the detector is the thing that's broken.
  4. Stickiness is a performance optimization, never a correctness requirement.
  5. Don't touch shared infrastructure until you can explain the symptom.

Your turn

Design challenge

Brightcart adds live video shopping: WebSocket connections that stay open 45 minutes on average, 200k concurrent at peak. You need to deploy a new version of the WebSocket servers twice a day without dropping viewers.

L4 or L7? Which algorithm? How do you drain a server during deploys? What happens when you add 10 new servers mid-show?

Hints
  • With long-lived connections, "least connections" means something very different than with 50ms requests.
  • New servers start with zero connections. Do they get flooded, or ignored?
  • Draining: stop new connections, then ask clients to reconnect gradually, with jitter.
What a strong answer covers
  • Connection draining with a deadline plus a server-sent "reconnect" message with random delay, to avoid a thundering-herd reconnect.
  • Balancing on connections rather than requests. New servers fill up only gradually, since existing connections don't move.
  • A client-side reconnect strategy with exponential backoff and jitter, and resumable session state stored outside the socket server.
  • L4 for raw connection throughput, or L7 if you need path or auth routing at the edge.
