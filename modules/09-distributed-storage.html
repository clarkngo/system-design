M

Morgan · Staff SRE · 14 years on-call

Storage is where "eventually we'll fix it" becomes "we lost customer data." Three questions for any storage design: what's the access pattern, what failures does it survive, and what's the blast radius when an operator gets it wrong? That last one is the one people forget.

Decision 1 · Migration plan

Where should 40 TB of photos, videos and PDFs live?

That buys about 8 years of headroom and fixes the single power supply. But it's still a shared POSIX filesystem mounted by 64 servers: one bad client can lock it up, scaling past one appliance is painful, and serving images to users still goes through your app servers. A sturdier version of the same architecture.

Photos are write-once, read-many blobs addressed by key, which is exactly what object storage is for. It scales to petabytes without you managing disks, replicates across failure domains, and the CDN serves images straight to users without touching your app servers. Uploads go directly from the browser to storage using pre-signed URLs.

A block volume generally attaches to one server at a time, so a photo uploaded to server 12 doesn't exist on server 40. You'd have to build your own replication and lookup layer, which means writing a distributed file system by accident. Block storage is for databases and boot disks, not shared media.

The CFO wants cheaper storage for 7 years of invoice PDFs (compliance archive, rarely read, legally required to keep). The team decides to run a small self-hosted object store on 12 servers across 2 racks in one data center and 2 more racks in a second site. How should the data be protected?

Decision 2 · Durability design

How do you protect the archive?

"Least-full disks" turn out to be the three new disks someone just installed, all in the same rack. Eight months later that rack's top-of-rack switch and power distribution unit fail together. All 3 copies of 140,000 invoices are unreachable at once, and two disks don't come back. Replicas only help if they fail independently.

Each object is split into 12 chunks, any 8 of which can rebuild it. Placement is failure-domain aware, so losing a disk, a server or a whole rack costs only a few chunks. Storage overhead is 1.5x instead of 3x. The trade-off is that reads and rebuilds need CPU and touch many servers, which is fine for a cold archive.

Solid durability with rack-aware placement, and simple, fast reads. But it costs 3x the raw storage for data almost nobody reads, and all three copies are still in one or two sites. Correct, expensive, and fine if budget isn't tight.

Month 10, Tuesday 09:35. The billing subsystem of your object store is running slow. The runbook says to remove a few servers from the billing pool and let them be re-provisioned. It's a routine command the team has run dozens of times:

$ storectl remove-capacity --pool billing --count 2

Your teammate types it out and shares their screen. You notice the command says --count 20. And the billing pool shares servers with the index subsystem: the metadata layer that knows where every object lives.

Decision 3 · 09:37 · Enter not yet pressed

The typo is caught this time. What do you change so it can't happen next time?

You caught it today because you happened to be watching. "Be more careful" isn't a control. People get tired, and someone will make this mistake at 2am. Same tool, same risk, next month.

You moved safety from human memory into the system. Even a fat-fingered --count 200 now removes servers gradually and stops at the floor. The dry run prints "This will remove 9 servers from the index subsystem" in red. This is almost exactly what AWS did after the real version of this incident.

Low traffic doesn't make a bad command safe. If the index layer loses too much capacity, it needs a full restart whether it's 3am or 3pm, and nobody has restarted it in years. The difference is that at 3am, fewer people are awake to help.

What you just learned

Object vs. block vs. file storage

ObjectBlockFile
UnitWhole object + metadata, by keyFixed-size blocks, like a raw diskFiles in directories (POSIX)
AccessHTTP API (PUT/GET), many clientsOne server mounts itMany servers mount it (NFS/SMB)
ScaleEffectively unlimitedVolume-sizedAppliance or cluster-sized
ExamplesS3, GCS, Azure Blob, MinIO, Ceph RGWEBS, Persistent Disk, SANNFS, EFS, NAS
Use forMedia, backups, data lakes, static assetsDatabases, VM boot disksLegacy apps, shared home directories

How distributed file systems work (GFS / HDFS)

  • Files are split into large chunks/blocks (64 MB in GFS, 128 MB by default in HDFS).
  • A metadata server (GFS master / HDFS NameNode) knows which servers hold which chunks. Data servers (chunkservers / DataNodes) store the bytes.
  • Clients ask the metadata server where the data is, then read it directly from the data servers, so the metadata server stays out of the data path.
  • Chunks are replicated 3x by default, with rack-aware placement.
  • Designed for write-once, read-many, large streaming reads (batch analytics). Bad at lots of tiny files and random writes.
  • The metadata service is the critical piece. It's what the AWS incident below took out.

Durability: replication vs. erasure coding

3x replicationErasure coding (e.g. 8+4)
Storage overhead3.0x1.5x
Survives2 lost copiesAny 4 lost chunks
Read costRead from any one copy, fastRead from several nodes. Reconstruction costs CPU
Best forHot data, small objectsWarm or cold data, large objects, archives

Either way, failure domains matter more than the number of copies: disk → server → rack → power and network zone → building → region. Correlated failures (same rack, same firmware bug, same operator command) are what actually lose data.

It happened for real

Real postmortems

Amazon S3 · us-east-1Feb 28, 2017 · ~4 hours

At 9:37 AM PST, an authorized S3 team member following an established playbook ran a command to remove a small number of servers from a subsystem used by S3 billing. One of the inputs was entered incorrectly, and a much larger set of servers was removed, including servers supporting the index subsystem (the metadata for every object in the region) and the placement subsystem (which allocates storage for new objects). Both needed a full restart, which hadn't been done in the larger regions for many years, and took hours given S3's growth. S3 wasn't fully recovered until 1:54 PM. Even AWS's Service Health Dashboard couldn't be updated, because its admin console depended on S3.

AWS's fix: change the tool to remove capacity more slowly, and add safeguards so capacity can't be removed below a subsystem's minimum required level.

Lesson: Decision 3, almost word for word. Design tools so the dangerous input is impossible, not merely discouraged. Restart your critical subsystems regularly, so you know how long it takes. And don't host your status page on the thing it reports on.

Source: AWS: Summary of the Amazon S3 Service Disruption in the Northern Virginia (US-EAST-1) Region

Google · The Google File SystemSOSP 2003

The GFS paper starts from a striking premise: with thousands of commodity machines, component failure is the norm, not the exception. So the design assumes disks, machines and networks fail constantly, and builds in replication, checksums and automatic re-replication. It became the blueprint for HDFS and much of modern big-data storage.

Lesson: at scale, failure is a constant background condition, not an event. Design for it, monitor for it, and let the system repair itself.

Source: The Google File System (PDF)

Field notes

Morgan's rules of thumb

  1. Blobs go in object storage. Only keys and metadata go in your database.
  2. Count failure domains, not copies. Three replicas in one rack is one replica.
  3. Safety belongs in the tool, not in "be careful": rate limits, floors, dry runs, approvals.
  4. If you haven't restarted it recently, you don't know how long a restart takes.
  5. Your status page must not depend on what it's reporting on.

Your turn

Design challenge

Design Brightcart's seller photo pipeline. Sellers upload 2 million photos a day (up to 25 MB each). Each photo needs 5 resized variants (thumbnail to zoom), served worldwide. Photos for deleted listings must be purged within 30 days (privacy law). Lost photos mean angry sellers.

Sketch the upload path, processing, storage layout, serving path, and deletion.

Hints
  • Should a 25 MB upload pass through your app servers at all? (Pre-signed URLs.)
  • Resizing is async work: queue, workers, idempotency (Incident 05).
  • Do you store all 5 variants, or generate some on demand at the edge?
What a strong answer covers
  • Browser → pre-signed PUT → object store. An object-created event → queue → idempotent resize workers.
  • Originals and variants in object storage with lifecycle rules (cheaper tier for old originals), and a CDN for serving with content-addressed keys.
  • Deletion via soft delete, then a lifecycle or batch job within 30 days, plus CDN purge and verification.
  • Cross-region replication or erasure coding for durability, and versioning against accidental deletes.
