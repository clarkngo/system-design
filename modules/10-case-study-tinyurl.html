Month 12 · Case Study: URL Shortener

Your First Design Review

Mon 09:01 @priya (Marketing): Must-haves: short links, click analytics per link, and links people can't guess (some are private early-access sale links).
M

Morgan · Staff SRE · 14 years on-call

A year ago you didn't know why sessions break when you scale out. Now you're running the review. Here's how Rhea runs these: requirements, then numbers, then design, then "what breaks first." She will ask about the requirement you forgot. Re-read Priya's message.

Step 1

Requirements

Functional

  • Given a long URL, return a short URL like brt.ly/aZ3k9Qx using characters [a-zA-Z0-9].
  • Visiting the short URL redirects to the long URL.
  • Count clicks per link (by day, country and referrer).
  • Optional: custom aliases (brt.ly/blackfriday) and expiry.

Non-functional

  • Redirects are fast (p99 < 50ms at the edge) and highly available. A broken link in a 5-million-recipient SMS is a disaster.
  • Short codes are not guessable or enumerable (private sale links).
  • Read-heavy: about 100 redirects per link created.

Step 3

The design review

Rhea's first question

"How do you generate the short code?"

Rhea: "Codes are sequential. If I get brt.ly/4kZ9, I can try 4kZa, 4kZb… and walk every private early-access link you've ever made. That violates a stated requirement. Also, who owns the counter? It's a single point of coordination." This is the standard textbook answer, and it fails Priya's requirement.

Not guessable from outside, which is good. But truncating means collisions, so you still need a check-and-retry. And the same long URL always produces the same code, so two campaigns linking to the same page share analytics, and anyone who knows the long URL can compute its code. Workable if you add a salt and collision handling.

Unguessable: about 3.5 trillion possibilities with only 0.2% used, so random probing almost always misses (add rate limiting on 404s to make scanning pointless). No central counter, since any server can generate codes. Collisions are rare and caught by the unique constraint. Rhea nods: "And custom aliases?" You: "Same table, and the same uniqueness check."

Morgan's question

"Which HTTP status does the redirect return?"

Morgan: "Exactly. Browsers cache it. After the first click, a user's repeat clicks never reach your server, so your click analytics undercount. You also can't change or disable a link once browsers have cached it, for example if a campaign URL is wrong or a link gets abused." 301 is fine for permanent site moves. It conflicts with the analytics requirement.

Every click reaches your edge, analytics are complete, and you can update or kill a link instantly. The cost is one extra round trip on repeat clicks, which you keep cheap by serving redirects from the edge (next decision). Morgan: "Good. You remembered Priya's requirement."

It works and gives you rich client-side analytics, but it adds a page load to every click, breaks for clients without JavaScript (some SMS previews, bots, curl), and confuses link-preview crawlers. Use a real 3xx unless you truly need an interstitial page.

Step 4

The architecture you present

                         ┌──────────── create path (≈40/s) ─────────────┐
 Marketer ── POST /links ─▶ API (auth, rate limit) ─▶ Links DB (KV / Postgres)
                                                         code ─▶ long_url, owner, expiry
                         └───────────────────────────────────────────────┘

                         ┌──────────── redirect path (4k–40k/s) ─────────┐
 Clicker ── GET /aZ3k9Qx ─▶ Edge / CDN worker ─▶ local cache ─▶ Redis ─▶ Links DB
                              │  302 + Location
                              └─▶ click event ─▶ Kafka ─▶ stream aggregator ─▶ Analytics store
                         └───────────────────────────────────────────────┘
  • Links DB: a key-value lookup by code. DynamoDB or Cassandra scale trivially, and Postgres is also fine at 3 TB with replicas. (Incident 04: choose by access pattern.)
  • Cache layers: link mappings almost never change, so cache them aggressively at the edge and in Redis, with jittered TTLs and request coalescing. (Incident 03.)
  • Clicks: fire-and-forget events to a log, aggregated asynchronously. Never write to the database on the redirect path. (Incident 05.)
  • API: idempotent creation, per-key rate limits, abuse checks on submitted URLs. (Incident 07.)

Approved. Launch is in three weeks.

Launch +6d 19:02 a celebrity with 90M followers posts brt.ly/kX8pQ2m (Brightcart collab drop)
19:03 redirects/s: 212,000 → 96% for one code
19:03 links-db shard 7 cpu 100% click_count UPDATE lock waits 38s
19:03 SEV1 redirect p99 9.4s (all links on shard 7)

It turns out someone added a "quick" feature after the review: UPDATE links SET click_count = click_count + 1 on every redirect, for a live counter in the dashboard. One row is now taking 200,000 writes a second.

Launch day · 19:04

One link, 200k clicks/second. Fix it.

A hot key isn't fixed by more shards: one code always lives on one shard. Resharding live during a spike makes everything worse, and the celebrity's link still hammers a single row. (Incident 01, Decision 3, all over again.)

The lock contention vanishes immediately, because the redirect path is now read-only and cached at the edge. Clicks flow into the log at 200k/s, which is easy for a partitioned stream. The dashboard counter updates every few seconds from the aggregator, which is plenty "live." p99 back to 22ms by 19:09. The drop sells out and nobody outside the team knows how close it came.

Redirects recover in 2 minutes, and you've stopped the bleeding. But marketing loses analytics for the single most valuable link they've ever had, which was the whole point of the product. Fine as an emergency stopgap, but you still need the async design.

What interviewers listen for

  • You clarified requirements and caught the one that changes the design (non-guessable, analytics).
  • You did estimates and let them guide you: "storage is small, reads and analytics are the problem."
  • You named trade-offs (301 vs 302, counter vs random vs hash) instead of reciting one answer.
  • You asked "what breaks first?" unprompted: the hot key, the synchronous counter.

It happened for real

The same pattern at bigger scale

Discord · Hot partitions2022

Discord's messages database struggled with "hot partitions": a single huge server's busy channel concentrating reads on one partition, which slowed down the entire cluster. Their fix included a request-coalescing data service in front of the database, so many simultaneous requests for the same data become one query. It's the same move you made for the viral link.

Lesson: hot keys are inevitable in anything social or viral. Coalesce reads, cache at the edge, and keep writes off the hot row.

Source: Discord: How Discord Stores Trillions of Messages

Field notes

Morgan's rules of thumb, the full year

  1. Ask "what breaks first?" before "how do we scale?"
  2. Requirements hide in other people's sentences. Re-read them.
  3. Estimate first. The numbers tell you which problem you actually have.
  4. Keep the hot path read-only and cached. Push writes and side effects to async pipelines.
  5. Every design decision is a trade-off. If you can't name what you gave up, you haven't understood it.
