Module 10: Case Study - TinyURL

Back to Home

Problem Statement

Design a URL shortening service like TinyURL. The service should take a long URL and generate a unique, short URL. When a user visits the short URL, they should be redirected to the original long URL.

Requirements

  • Functional:
    • Given a long URL, return a short URL.
    • Given a short URL, redirect to the original long URL.
    • The short URL should be a combination of characters `[a-zA-Z0-9]`.
  • Non-Functional:
    • The service should be highly available.
    • The redirection should be fast (low latency).
    • The short URLs should not be guessable.

High-Level Design

The core of the service is a key-value store where the key is the short URL and the value is the long URL.

  1. The client sends a long URL to the service.
  2. The service generates a unique short URL. A common approach is to use a base62 encoding of a counter.
  3. The service stores the mapping between the short URL and the long URL in a database.
  4. The service returns the short URL to the client.

Redirection

  1. The user clicks on the short URL.
  2. The browser sends an HTTP request to the service.
  3. The service looks up the long URL in the database using the short URL as the key.
  4. The service sends an HTTP 301 redirect response to the browser with the long URL in the `Location` header.
  5. The browser redirects to the long URL.

Further Considerations

  • Database Choice: A NoSQL database like Redis or Cassandra would be a good choice for its fast key-value lookups and scalability.
  • Scalability: The service can be scaled horizontally by adding more servers behind a load balancer. The database can be sharded to distribute the data.
  • Analytics: We could add an analytics service that tracks how many times a short URL is clicked.
