An API is a promise to code you don't control and can't redeploy. Your server ships 20 times a day. Someone's phone updates whenever it feels like it. Design for the oldest client still out there.

Decision 1 · After the rollback

How should the team make changes like this from now on?

The mobile team releases 4.13, and 30% of users still don't update for months. Next Tuesday, the same crash returns. You can't force-upgrade a phone. Breaking changes have to be opt-in.

Safe, but a year later you're maintaining /v2 through /v9, each with slightly different handlers, test suites and bugs. Versioning is for breaking changes you truly can't avoid. Most changes can be additive.

Old clients keep working, and new clients get the better field. A Deprecation or Sunset header plus usage metrics tell you when removal is safe. Add CI contract tests that fail a PR if it removes or renames a field in the public schema, and this class of incident is gone.

Month 7, week 3. A large partner, MegaMart, reports something strange: their system shows 1 order, but Brightcart shipped 3 identical ones.

14:02:11.004 POST /orders partner=megamart → 201 in 11.2s (order 88121)
14:02:21.010 POST /orders partner=megamart → 201 in 9.8s (order 88134) client timeout=10s, retry 1
14:02:31.020 POST /orders partner=megamart → 201 in 4.1s (order 88140) retry 2

MegaMart's client times out after 10 seconds and retries. But Brightcart's server didn't fail. It was just slow, and completed every attempt.

Decision 2 · Partner escalation

How do you prevent duplicate orders from retries?

Now when a request genuinely fails (network blip, deploy, load balancer reset), partners just… lose the order. Over an unreliable network, the client can't tell "failed" from "succeeded but the response got lost." Banning retries trades duplicates for lost orders.

Retries become safe: the second and third POSTs with the same key return order 88121 instead of creating new ones. Details that matter: scope keys per API client, keep them for 24 hours or more, store the key in the same transaction as the order, and return 409 if a request with the same key is still being processed. This is exactly how Stripe's API works.

Technically sound: PUT to a client-chosen ID is naturally idempotent. But it's a breaking contract change for 40 partners (see Decision 1), and client-generated IDs need validation against collisions and abuse. A good design for a new API, but a heavy migration for an existing one.

Decision 3 · 17:54

How do you protect everyone else?

You're paying to serve a bug. The database can't autoscale in minutes anyway, and the partner's loop gets faster as your responses get faster. By Monday you have an expensive bill and an unhappy DBA.

QuickShip gets its fair share (say 200 req/s with bursts up to 400) and a clear 429. Everyone else is unaffected within a minute. Per-key limits make one tenant's bug that tenant's problem, the core idea of multi-tenant isolation. You also email QuickShip, which is the human half of the fix.

It stops the flood, and also their legitimate order traffic, so you've taken a partner fully offline on a Friday evening. Their IPs are cloud NAT addresses shared with another partner, so that partner goes down too. A blunt tool that works, with collateral damage.

Designing for evolution

  • Additive changes are free: new fields, new endpoints, new optional parameters. Clients must ignore unknown fields.
  • Breaking changes: removing or renaming fields, changing types or meanings, making something required. These need a new version and a deprecation window.
  • Versioning schemes: in the URL (/v2/, simple and visible), a header, or date-based (Stripe pins each account to an API version date).
  • Pagination: prefer cursor-based (?after=abc123) over offset. Offsets get slow on big tables and skip or repeat items when rows are inserted.

The API gateway's job

A single entry point that handles cross-cutting concerns so each service doesn't have to: authentication (API keys, OAuth/JWT), rate limiting and quotas per client, routing to services, request and response transformation, caching, TLS termination, and metrics per client. Rate-limiting algorithms: token bucket (allows bursts, the common choice), leaky bucket (smooth output), fixed or sliding window counters.

Retries: helpful or harmful?

Naive retries multiply load exactly when a system is struggling. If 3 layers each retry 3 times, one user request becomes up to 27 backend calls. The rules: retry only idempotent operations, use exponential backoff with jitter (random spread so clients don't retry in sync), cap total attempts, use a retry budget (e.g. retries at most 10% of traffic), and honor Retry-After.

It happened for real

Real postmortems

AWS · us-east-1 internal networkDec 7, 2021 · ~7 hours

An automated activity to scale an internal AWS service triggered unexpected behavior in a large number of clients on the internal network, a surge of connection activity that overwhelmed the networking devices between two networks. The resulting latency and errors caused even more connection attempts and retries, which kept the devices congested. The congestion also took out the internal monitoring that engineers needed to diagnose the problem.

Lesson: retries are load. Under stress, clients that retry without backoff, jitter and a budget turn a blip into a sustained outage.

Source: AWS: Summary of the AWS Service Event in the Northern Virginia (US-EAST-1) Region

AWS Architecture Blog · Exponential Backoff and Jitter2015

Marc Brooker simulated clients competing for a contended resource and showed that exponential backoff alone still produces synchronized waves of retries. Adding randomness ("full jitter": sleep a random time between 0 and the backoff cap) dramatically reduced both total work and completion time.

Lesson: sleep = random(0, min(cap, base × 2^attempt)). Memorize it, and put it in every client SDK you ship.

Source: AWS Architecture Blog: Exponential Backoff And Jitter

Stripe · Idempotency keys in practice2017

Stripe's API accepts an Idempotency-Key on every POST and stores the result, so clients can retry safely after any network failure. Their write-up covers the design, including why the client generates the key and how to combine it with backoff.

Source: Stripe: Designing robust and predictable APIs with idempotency

Field notes

Morgan's rules of thumb

  1. Never remove or rename a public field. Add, deprecate, measure, then remove.
  2. Every POST that creates something takes an idempotency key.
  3. Rate-limit per client, not globally. One tenant's bug shouldn't be everyone's outage.
  4. Retries need backoff, jitter and a budget, or they become a DDoS on yourself.
  5. Use cursor pagination. Offset pagination is a slow query waiting to happen.

Define the endpoints, the idempotency approach, pagination, error format, rate limits, and how partners learn about shipping without polling.

Hints
  • "Cancel" is a state transition. Should it be DELETE or POST /orders/{id}/cancel?
  • Webhooks also need retries, signatures and idempotency on the receiving side.
What a strong answer covers
  • POST /v1/orders with an Idempotency-Key, GET /v1/orders/{id}, GET /v1/orders?after=cursor&limit=100, and POST /v1/orders/{id}/cancel (idempotent).
  • A consistent error format with a machine-readable code, and 429s with Retry-After.
  • Signed webhooks with event IDs (so receivers can deduplicate), retries with backoff, and an events list endpoint to catch up.
  • A versioning and deprecation policy published from day one.
