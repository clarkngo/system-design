Month 6 · Content Delivery Networks

The Cache That Leaked Accounts

  • Role: on-call during Black Friday week
  • 3 decisions
  • ~15 min
Mon 09:15 origin-web bandwidth 8.7 Gbps / 10 Gbps 78% of bytes: /images/* /static/*
Mon 09:15 p95 page load (Sydney): 6.8s (Virginia: 1.1s)
Mon 09:16 @devin: Black Friday is Friday. Traffic forecast 6x. We can't 6x our origin bandwidth by Friday.

Brightcart serves everything (HTML, JavaScript, CSS and 2 million product images) from origin servers in one region: us-east. Australian customers wait almost 7 seconds per page, because every request crosses the Pacific twice. And the origin's network link is nearly full.

M

Morgan · Staff SRE · 14 years on-call

The speed of light is the one dependency you can't optimize. Sydney to Virginia is about 200ms round trip, before any TLS handshake. The fastest request is the one that never reaches your origin. But careful: a CDN is a cache with 300 locations and a global config switch. Respect it.

Decision 1 · Monday

How do you get through Black Friday?

The network upgrade has a 3-week lead time. Even if it arrived, Sydney would still take 6.8 seconds: bandwidth doesn't fix latency. And you're paying to serve the same unchanging JPEG 40 million times from one building.

On the first request for /images/sku-1182.jpg, the Sydney edge fetches it from origin once, then serves every Australian customer from Sydney. With Cache-Control: public, max-age=31536000, immutable and filenames that change when the content changes, the cache hit ratio reaches 96%. Origin bandwidth drops to 1.2 Gbps and Sydney loads pages in 1.9 seconds.

It works. But now every new product image needs an upload pipeline, deletes need syncing, and you're storing (and paying for) 2 million images in every region, including long-tail ones nobody views. Push suits large, rarely changing files like video or installers. For a catalog, pull is simpler.

Wednesday. The frontend team deploys a new checkout page. Within minutes:

Wed 14:02 js errors/min 4,120 "TypeError: initCheckoutV2 is not a function"
Wed 14:02 checkout conversion −38%

The new HTML calls initCheckoutV2(), but the CDN is serving the old /static/app.js from cache. It was uploaded under the same filename with a 24-hour max-age.

Decision 2 · 14:04

Fix it now, and make sure it never happens again.

It fixes the JS, and empties every edge everywhere at the same moment. Two days before Black Friday, 2 million images all miss at once and the origin link hits 10 Gbps. You just recreated the cold-cache stampede from Incident 03 on a global scale. Purge narrowly (one path) and fix the naming so you rarely need to purge at all.

This is the standard pattern. Content-hashed assets never change, so they can be cached forever. A new deploy produces new filenames, and the short-lived HTML points to them. There's never a mismatch, and you almost never need to purge. Rollback is easy too: the old files are still there.

A hard refresh can't touch the CDN edge cache, only the browser's. Users refresh and get the same stale file from the Sydney edge. 4,000 errors a minute continue for 24 hours, and your social post goes semi-viral for the wrong reasons.

Black Friday, 16:05. Origin CPU is high, so an engineer on the platform team adds a CDN rule to cache /account/* pages for 5 minutes, "to take load off origin." It ships globally at 16:08.

16:19 #support: "I'm logged in but the page shows someone else's name and address??"
16:20 #support: "my order history has orders I never made"
16:20 SEV0 security: possible PII exposure

The CDN's cache key is the URL. /account/orders is the same URL for every user. The first user to load it got their page cached, and everyone after them in that region is seeing it.

Decision 3 · 16:21 · personal data is leaking every second

What do you do first?

Scoping the damage matters, but not first. Every minute you spend in logs, more users' addresses and order histories are served to strangers. The investigation takes 35 minutes, and the leak runs the whole time. In a data exposure, contain first, then investigate.

The leaked pages disappear, and the very next request re-caches someone's account page, because the rule is still live. You're bailing water without plugging the hole. It buys about 30 seconds.

Contain (roll back the rule), clean up (purge), then defend in depth: even if someone adds a bad rule again, origin explicitly marks personalized pages as uncacheable, and you add a CDN policy to never cache responses that set cookies or depend on an Authorization header. Then scope the impact from logs and notify affected users. Leak window: 13 minutes.

Debrief

What you just learned

How a CDN works

  1. The user's DNS lookup (or anycast routing) sends them to the nearest edge PoP, one of hundreds worldwide.
  2. The edge checks its cache using the cache key (by default roughly host + path + query string).
  3. Hit: serve from the edge, in milliseconds. Miss: fetch from origin (often via a regional origin shield so 300 edges don't all hit origin), store it, serve it.
  4. Bonus: TLS terminates close to the user, and the CDN soaks up DDoS traffic before it reaches you.

Pull vs. push

Pull zonePush zone
HowEdge fetches from origin on first missYou upload content to CDN storage
Good forWebsites, catalogs, APIs. The defaultBig, rarely changing files: video, game patches, installers
Watch outFirst request per region is slow, and cold-cache stampedesSync pipeline, storage cost for the long tail

Cache-Control cheat sheet

DirectiveMeaningUse for
public, max-age=31536000, immutableAnyone may cache it for a year, and it never changesContent-hashed JS, CSS and images
public, max-age=60, s-maxage=300Browsers keep it 60s, shared caches (CDN) 300sPublic pages that change occasionally
stale-while-revalidate=30Serve stale while refreshing in the backgroundSmoothing over origin slowness
privateOnly the user's browser may cache it, not shared cachesPersonalized pages
no-storeNobody stores it, anywhereAccount pages, PII, payment pages

Invalidation strategies

  • Versioned (content-hashed) URLs: the best option. Never invalidate, just change the name.
  • Targeted purge: purge by path or surrogate key/tag (e.g. every page tagged product-1182).
  • Short TTL + stale-while-revalidate: freshness and resilience together.
  • Global purge: a last resort. It's a self-inflicted stampede.

It happened for real

Real postmortems

Valve · Steam StoreDec 25, 2015 · ~90 minutes

During a Christmas DDoS attack, with traffic about 2,000% above a typical Steam Sale, Valve's web-caching partner deployed more aggressive caching rules to protect the origin. One rule was misconfigured, and pages generated for one logged-in user were served to others. For about 34,000 users, store pages containing billing addresses, purchase history, partial card digits and email addresses may have been seen by other users.

Lesson: Decision 3, for real. A caching change made under pressure to protect the origin exposed personal data. Personalized responses must be uncacheable by default at origin, so a CDN rule can't override it by mistake.

Source: Steam: Security Update (Valve statement)

Fastly · Global outageJun 8, 2021 · ~49 minutes

A software deploy on May 12 introduced a latent bug that a specific, valid customer configuration could trigger. On June 8, a customer pushed exactly that configuration. It propagated globally, and 85% of Fastly's network began returning errors. Major news sites, retailers and government sites went down at once. Fastly found the cause within minutes and recovered 95% of the network in 49 minutes.

Lesson: a CDN is a globally distributed system with a global config plane. One bad config can reach every edge in seconds.

Source: Fastly: Summary of June 8 outage

Cloudflare · WAF regexJul 2, 2019 · 27 minutes

A new WAF (web application firewall) rule contained a regular expression that backtracked catastrophically. It was deployed globally at once and drove CPUs to nearly 100% on every core handling HTTP traffic, across Cloudflare's entire network. Proxying, CDN and WAF went down for 27 minutes.

Lesson: roll out edge config the way you roll out code: canary first, then staged, with automatic rollback. A change that goes everywhere at once fails everywhere at once.

Source: Cloudflare: Details of the Cloudflare outage on July 2, 2019

Field notes

Morgan's rules of thumb

  1. Content-hash your assets and cache them forever. Keep HTML short-lived.
  2. Personalized responses get private, no-store at origin. Don't rely on the CDN config alone.
  3. Know your cache key. If the response varies by something that's not in the key, you will leak or corrupt.
  4. Purge narrowly. A global purge is a self-inflicted stampede.
  5. In a data leak: contain, clean up, then investigate. In that order.

Your turn

Design challenge

Cache the product page. Brightcart's product page HTML is 95% identical for everyone (title, photos, description, reviews) but shows a personalized header ("Hi, Ana · 3 items in cart") and region-specific prices (USD, AUD, JPY).

Can you cache it at the CDN? How? What goes in the cache key? How do you update the price within 60 seconds of a change?

Hints
  • Split the page: cache the shared shell, fetch the personalized bits separately (client-side, or edge-side includes).
  • Currency could go in the URL or the cache key (Vary-style), but never the user's identity.
  • Surrogate keys / cache tags let you purge "every page that shows SKU 1182".
What a strong answer covers
  • A cacheable shell keyed by path + region or currency, with a short TTL plus stale-while-revalidate.
  • The personalized header loaded via an uncacheable API call (private, no-store).
  • Tag-based purge on price change, with the TTL as backstop. Possibly edge compute for the composition.
  • An explicit check that no Set-Cookie is ever present on cached responses.
